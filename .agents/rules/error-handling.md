# 错误处理规则

- 面向用户的 UI、Toast、SnackBar、Dialog 等展示中，禁止直接透出底层异常对象、SDK 原始报错、堆栈、完整响应体（JSON / HTML）或 `DioException.toString()`；此限制不适用于返回给 Agent 的工具结果。
- 服务商在响应中返回的可读错误文案（如 `error.message`，用 `tryReadProviderMessage` 提取）不属于底层报错，界面可以直接展示。
- 返回给 Agent 的工具结果应保留实际错误码、底层错误消息及命令诊断日志，供 Agent 判断原因和处理失败；不得仅返回笼统的“操作失败”，或只把详情写入日志而不提供给 Agent。
- 用户界面应将底层错误转换为用户可理解的说明；开发排查所需的技术细节同时写入日志，不因用户展示要求而删减 Agent 工具结果中的诊断信息。
- 涉及 HTTP / SDK 调用失败时，日志必须尽量包含请求目标、状态码、异常类型，以及服务端错误返回体或响应体内容，避免只打印一句失败信息。
- **所有数据库写入操作必须用 try-catch 包裹并加 `[DB]` 日志**。禁止让 Drift/SQLite 异常静默传播或被上层泛化 catch 吞掉。日志必须包含表名、操作类型（INSERT/UPDATE/DELETE）、记录 ID 和完整异常信息。

## 兜底逻辑规则

- 不要为缺失依赖、配置错误、初始化顺序错误、权限不满足、数据状态不符合预期等问题添加静默兜底逻辑。
- 预期应该报错的场景必须明确报错或返回明确失败状态，禁止用空结果、默认对象、跳过执行、降级到另一条逻辑链路等方式掩盖问题。
- 只有产品需求明确允许降级，且降级行为对用户可见、可解释、可测试时，才可以添加 fallback。

## 必备依赖

- 初始化或构造完成后必定存在的 service、config、manager、client 等依赖，调用侧直接使用，不添加 `if (x == null)`、空结果或 fallback 来掩盖初始化错误。
- 只有“依赖确实可选”是明确设计的一部分时才允许判空；可选分支必须有独立、可解释、可测试的行为。
