# 应用内技能的划分与维护

适用于 `assets/bundled_skills/`、`assets/official_skills/` 及其注册、加载和调用入口；不适用于供代码开发使用的 `.agents/skills/`。

**业务决定 Skill 入口，功能决定附件，基础性决定 bundled / official 归属。**

## Skill 边界与触发

- 按用户要完成的完整业务任务划分 Skill，不按 Read / Write / Run 等工具名称或界面容器划分。导演台人物、机位和时间轴属于剧本制片业务，不因显示在画布节点中就归入构思画布。
- `when_to_use` 写清用户意图、操作对象和任务阶段，并说明容易混淆的相邻任务边界。例如“正文完成或返工后的事实整理”归故事连续性维护，“讨论尚未发生的剧情”不触发事实写入。
- 不为减少 Skill 数量，把不同业务入口合成一个泛化的“工具使用”Skill。多个任务调用同一个工具，不是合并它们的理由。
- 同一业务所必需的方法与操作可以共存。不要为“工具说明／创作方法”的形式分离，拆散开书、制片或写后事实维护等完整流程。
- 技能的触发词、任务分段标题和反馈用语对齐实际 UI 名称；涉及内部资源名时明确映射。例如区分界面“分镜”、提示词中的 Shot 镜头和剪辑时间线的片段，不能用“分段”等自造名称替代。修改前核对桌面／移动端入口与翻译资源。
- 名称描述实际职责；“指南”“规范”等后缀不决定内容归属，也不能代替清晰的触发边界。

新增独立 Skill 前必须判断：用户是否会独立提出该任务、它是否有可区分的触发条件、拆分是否能减少无关加载并保留完整流程。仅是已有任务的一个步骤或场景时，优先放进现有 Skill 的附件。

## Bundled 与 official

| 归属 | 判断标准 | 内容边界 |
| --- | --- | --- |
| `assets/bundled_skills/` | 应用默认提供、随应用维护的基础业务入口 | 可以同时包含完成任务必需的方法、操作契约和按需附件 |
| `assets/official_skills/` | 用户可选择、替换和定制的专业方法 | 补充写作、设计、分析或制作方法，不承担应用基本操作的唯一契约 |

- 创作向导、故事连续性维护、画布构图、媒体处理与剪辑保留为 bundled 业务入口；不因它们包含方法内容就迁入 official。
- 故事连续性维护保留正文事实提取、实体状态、关系、伏笔及 `story_state` 维护的完整入口，不拆散到泛化的“资料管理”中。
- 官方技能可以调用基础操作；操作契约由对应 bundled Skill 或工具 schema 维护，不复制进各个官方技能。
- 归属不能仅按是否打包在应用内、是否自动安装判断。官方技能的安装、停用、删除与自定义选择必须被尊重，不能假定每次调用时必然可用。

## 附件与内容归属

- 主文件保留任务目标、边界、共同原则与紧凑路由表；按功能或场景拆分 `references/`，执行对应环节前按需读取，不预读全部附件。
- **单一真源与上下文预算**：同一原则或流程只在一个最贴近主责的权威附件完整陈述，其他文件仅用一行链接引用，严禁跨 3 个以上附件反复复述“诚实交付、先看图再结论、单一变量排查”等通用准则；控制单文件与示例体积，只保留能改变当前决策的判断依据。
- **有向无环（DAG），禁止循环引用**：
  - **跨 Skill**：基础操作与契约（bundled Skill 与工具 schema）必须独立自足，不得要求先加载可选 official Skill 或彼此互为前置；official Skill 可单向引用工具技能的入口名，但两者不得形成双向加载循环。
  - **Skill 内部**：保持 `SKILL.md` → 入口 `references/` → 子规则／模型附件／案例的单向层次与单一真源；禁止同级 `references/` 互相“见对方再回来看”的乒乓互指，也不得让子附件反向依赖未加载的主入口或父附件才能理解（从父附件路由进来的子附件无需再反向挂“详见父附件”的回指链接，以免形成网状互指与重复加载冲动）。
  - **`<inline-ref>` 约束**：内置技能共用的小节使用 `<inline-ref type="reference" skill="调用名" section="二级标题">references/附件.md</inline-ref>` 引用且保持作品类型中性；引用不得嵌套或成环。跨目录复用附件（如挂载另一 Skill 下的文件）须保证解析路径唯一且持续被测试守卫。
- **创作、契约与代码真源严格对齐**：
  - 创作输出格式归对应方法 Skill（如 Shot 格式归剧本制片，剪辑流程归媒体处理与剪辑），JSON 结构、字段类型、枚举与参数约束归工具 schema 与 bundled 契约（遵循 `.agents/rules/ai-calling.md`），互不越界抄写。
  - Skill 正文中涉及模型清单、支持输入模式、频道参数（如是否存在 `negative_prompt`、`prompt_extend`、音频参考、单/多镜头配置）、渠道子型号差异以及应用内标签解析语法（如双属性 `<ref input_id="…" label="…" />`）时，**编写前必须核对当前代码实现与目录配置**。严禁把代码未接入的厂商参数写进正文中冒充可用功能，严禁在示例代码中使用解析器不认的简写占位（如 `<ref …/>`、`<ref 首帧/>`），并明确标注渠道差异与“以运行时查询为准”。

## 方法类 Skill 的内容质量

- **写给执行任务的模型。** 每段应提供设计判断、操作方法、必要约束或有效示例。研究过程、阅读日期、工作汇报、尚未验证的本轮状态、与用户的争论及自我辩解不进入运行时正文；完成状态在对话中报告。
- **泛化提炼，严禁针对单一问题硬编码打补丁。** 遇到具体故障或用户指出的局部问题时，必须下沉提炼**通用因果机制与触发边界**；严禁为了迎合单次反馈、特定人物/人群、单个道具或某个局部失误而硬编码死规则或另建特例文件（例如把局部权宜做法写成全局铁律：固定默认降噪/磨皮、固定 45° 俯视或 `16:9` 前缀、强制全员四区拼板、双遍否定词或“无人/无手/无文字”尾部拐杖）。
- **条件分支优于全局覆盖。** 确实只针对特定故障现象才需介入的补救手段（如出现噪点再降噪、多次重出稳定多余物再用 `--no`），必须写成“**仅当出现 X 现象时才做 Y**”的条件策略，不得写入常规主流程覆盖无关风格、质感或正常输入。
- **禁止固化样本与封闭清单。** 检查更换人物、物件、时代或场景后规则是否依然成立；不能只留下“写清楚、保持一致”等空泛口号，也不能把参考样本自动变成封闭分类、固定风格菜单、必做步骤数或默认角色库（用户明确要求模板库除外）。
- **案例多样且服务于推导。** 保留案例时须交代“设计取舍 + 可复用片段 + 验收条件”，不堆砌重复长段提示词；多个案例应刻意差异化人物、物件与场景（避免不同知识点全挤在同一个固定故事线里互相串戏或冲突）。
- **保留用户审美与任务范围。** 提炼方法时不擅自将华丽、时尚、性感或风格化设计改成日常、职业、克制或极简。自编示例服务于正在讲的方法，不引入无关人设或剧情替代原任务。
- **入口只负责路由。** 用简短的“何时读＋附件链接”即可，不在入口重复附件摘要、通用原则或本次纠偏说明。附件正文不反复声明“这是方法”“可以迁移”“不是固定分类”；通过内容组织体现这些要求。
- **来源与教学分清。** 外部链接不能代替自足的方法正文，也不要求执行时重新阅读原材料才能理解。署名与许可放在 Skill 根目录独立的 `NOTICE.md`，随资源打包，不注册为运行时 reference，也不在教学正文重复许可说明。学习方法不等于获得原文、图片的复制授权。
- **修订针对具体问题。** 提出修订建议前就读取本规则、目标正文及相关附件，先辨明用户是在纠正结构、范围、措辞还是方法本身。先核对现有方法是否已覆盖问题，再决定替换或补全原段落，保留已认可及仍有价值的内容。开发 Agent 的阅读纪律、沟通失误和维护经验归开发规则；运行时 Skill 只接收对业务任务有用的方法。

交付前通读主文件与改动附件：删去重复路由、冗余复述、过拟合特例和聊天残留；确认方法能跨场景迁移、示例能说明取舍、没有硬编码补丁与循环引用。静态检查不能代替这一步内容审阅。

## 打包官方技能按发布状态维护版本

- **打包官方技能按发布状态维护版本**：修改技能主文件或 references 附件前，先核对本地最新正式发布 tag 及其对应代码中的技能版本，不能仅凭当前分支、源码注释或版本号判断。当前技能版本已发布时，修改内容必须递增 `version`；经核实尚未发布时，将修改合并到当前版本，保持 `version` 不变。两种情况都同步更新 `contentHash` 和 `updatedAt`；hash 测试只校验内容一致性，不能证明是否需要升版本。保持版本号的开发修改不会触发已安装技能的自动升级，必须使用 SQLite skill 同步更新 Debug 数据库中该技能的官方安装快照、附件及相关内容指纹，并查询验证；没有安装记录时说明无需更新，不为此新增安装。保留安装 ID、启用状态、排序和历史记录，不覆盖已转本地或用户自定义的技能，不改 Release 数据库，也不为开发数据新增运行时兼容层。具体版本的发布状态只记录在本次核查结果中，不写入源码注释。

## 新增与调整时的检查

1. 先读相邻技能、附件及调用方，确认已有入口是否能承载任务，再决定新增 Skill、扩展附件或迁移内容；说明选择 bundled / official 的业务理由与单向依赖方向（无环）。
2. 用典型请求核对预期路由：应触发的任务、不应触发的相邻任务、需要多个附件或 Skill 的混合任务；同步评估单轮按需加载的附件总数与字符体量是否可控。静态文案检查不能声称已验证模型的实际触发准确率。
3. **增删、改名或修改标题后全量巡检**：检查注册表、资源声明、Run 命令映射、Agent 提示词及桌面／移动端入口；扫描所有相对 Markdown 链接、显式 `#anchor`、合法引用标签语法，以及是否存在残留旧文件名或跨附件循环引用；保留用户同名覆盖、停用和删除的既有语义。
4. 官方技能的版本、`contentHash`、`updatedAt` 及 Debug 快照同步按「打包官方技能按发布状态维护版本」执行；修改工具 description 遵循 `.agents/rules/ai-calling.md`。
5. 按 `.agents/rules/testing.md` 运行受影响的加载、附件、路由及官方内容指纹测试。仅修改本规则时检查文档 diff 与引用即可，不为文字规则新增 Flutter 测试。

主要维护入口：

- `lib/shared/services/bundled_control_skills.dart`：bundled 注册、命令映射与附件清单。
- `lib/shared/services/bundled_official_skills.dart`：official 注册、附件及版本元数据。
- `lib/shared/services/ai/chat_turn_runner.dart`：可用技能摘要、加载与同名覆盖。
- `lib/shared/services/official_skill_sync.dart`：官方技能安装与升级语义。
- `test/shared/services/bundled_control_skills_test.dart`、`test/shared/services/bundled_official_skills_test.dart`：资源加载与内容校验。
