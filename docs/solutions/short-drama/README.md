## 背景

已有剧本能表达季、集、场次与对白，但从文字进入拍摄规划、参考素材、生成和剪辑时还需在外部工具重复组织。现有构思画布不具备媒体输入与异步视频作业合同，场次板也不等于摄影分镜。该方案把这段制作过程接到现有作品与当前集，保留原内容系统。

## 决定与约束

- 制作默认值保存于 Screenplays，当前集画布关联在 ScreenplayEpisodes；ProductionClips 以 video/image/audio 区分媒体类型，以 sceneId/sortOrder 表达场次归属。直接成片只取场次内视频，顺序来自场次及场内排序，画布坐标不参与排序。
- 提示词使用独立的 `<ref file_path="…" label="…" />` 或 `<ref clip_id="…" label="…" />`，文件引用固定受控路径，节点引用在提交时解析采用文件。生成输入由画布边提供，已创建任务保存固定副本；提示词编辑不改变已提交请求。
- 采用结果由 selectedFilePath 保存，生成反馈由统一 GenerationTasks 派生；成功结果登记后应用到来源，应用标记防止迟到或重复回调覆盖人工选择。不新增手工制作三态。
- CanvasNodes 通过 refType/refId 引用生成节点或导演工程；素材节点通过 mediaPath/mediaType 读文件。Assets 提供资产目录与生成结果登记，不是文件读取的唯一身份。备份同时覆盖文件路径与资产引用。
- 图片、视频、音频任务复用 GenerationTasks 的来源、请求快照和结果指针，具体提交与恢复遵循各媒体服务合同。生成任务和结果资产在应用库事务登记，采用结果由内容库事务应用，跨库失败可恢复且不重提生成。
- 原内容、角色与地点模型保持现状；制作、导演与剪辑各自持有自己的编辑内容。导演目标实体为 VideoStagings，剪辑为 VideoEditings；episode 通过 editing_id 引用独立剪辑；新建集自动绑定空工程，已有集打开时为空则补建，当前制片场景每集一个。旧导演／剪辑数据不迁移、不兼容；导演历史机制继续使用 Revisions，原媒体和其他业务数据保留。
- Agent 全流程按 [Agent 接入合同](agent.md)执行：资源读写、生成、导演输出、剪辑和导出复用业务服务，文件内容仅通过 Run files 授权读取。权限按全局、整部作品、episode、session 分层，首批接入生成与文件读取。
- 方案只维护一个目标版本。Agent 剪辑暴露当前已实现的编辑命令及字幕输出；视频转场库、多版本分支等仍按非目标处理，FFmpeg 素材处理不等于时间线支持对应可编辑效果。
- 数据结构变更按实际发布记录与标签核定，历史版本号和“未发布”记录不能代替核查；不恢复旧独立设置表、旧任务表或新增不需要的兼容列。

## 范围与非目标

本方案包含：片段编辑与状态、统一资产库、图片/视频/音频导入、现有生图复用、整集制作画布、导演参考输出、视频生成与重做历史、结果采用、单段/按成片顺序批量视频导出、整集成片 MP4、Markdown/CSV 提示词表，以及内置多轨编辑、Agent 剪辑、音频混合、低清分段预览、工程自动保存、剪辑后成片导出、用户自配 S3 参考存储与音频生成节点。音频模型范围按[音频生成合同](audio-generation.md)及模型能力目录维护。另包含 [Agent 全流程](agent.md)、可扩展分层工具权限、providers 能力查询、Run files 文件读取和 Run ffmpeg 素材处理。桌面工作路径以 Windows / macOS 为本次验收范围；共享权限设置与审批同时覆盖 Android。

本方案不包含：专有制作包导入/导出、成本预估与供应商价格表、时间线变速与视频转场库、成片导出任务存档、移动端短剧制作、独立生成任务管理页面、内置视频模型、多人实时协作、多人审批流、复杂合成/调色界面、任意插件市场、独立全剧无人值守调度器、自动发布、精细动作捕捉、物理仿真、保证模型按三维轨迹执行、完整版本分支管理。导入音频和预览视频原声属于本方案。音频节点消费统一资产与制作画布，混音可独立使用导入音频，不以模型生成为前置条件。直接整集成片与多轨剪辑后成片均为当前完成条件，详见 [X 导出](production.md#导出)与 [C 剪辑](editing.md)。

用户自配 S3 兼容对象存储由任务 F 实现，用于生成前上传参考视频（包括导演预演），提供模型可读取的云端 URL；不用于保存生成结果。后续参考准备按 [参考素材上传与 Seedance Asset 认证](reference-upload.md)选择路径：已有认证 Asset 保留独立引用；本地图片／音频按 OSS、渠道上传、Base64 选路，渠道缓存只在无 OSS 且已选中渠道上传后复用；本地视频文件按 OSS、渠道上传选路，不使用 Base64。生成结果在所有阶段都下载保存到本地。文本与图片模型沿用既有渠道策略，本次只收窄视频生成来源。

支持某个模型不表示暴露其全部衍生 API；生成模式和排除范围在 [E1 模型接入](video-generation.md) 明确。用户数据默认软删除；CanvasEdges 关系行按用户于 2026-10-07 确认的例外保留硬删除，具体范围见[画布与输入关系](production.md#画布与输入关系)。工具 description 修改需单独确认、不得静默缩小平台范围等仓库约束继续生效。

## User Stories

1. 作为作者，我希望从当前集直接规划片段和镜头，并能随时打开来源场次，以便不重复整理已经写好的剧本。
2. 作为作者，我希望将角色图、场景图和导演预演组合到视频节点，并在提交前确认实际输入、请求数量和生成时长，以便只为需要的尝试付费。
3. 作为作者，我希望关闭页面后仍能找回原任务，下载失败只重新下载，以便不用重付生成费用。
4. 作为作者，我希望保存历次视频，生成结果登记后自动采用并显示任务完成，不满意可重做或切回历史结果，直接导出整集，或在应用内裁切、叠画、加入配音和 BGM 后导出。
5. 作为维护者，我希望 Seedance、H3、Wan 3.0 的协议与恢复有确定合同及故障用例，以便更换模型或排查问题时不改写作品数据。

6. 作为作者，我希望在聊天中描述制作目标，让 Agent 完成分镜、参考生成、剪辑及导出，并能查看、撤销可回退的编辑。
7. 作为作者，我希望按全局、整部作品、episode 或 session 设置工具权限，让已允许的生成和文件读取连续执行，需要询问时展示具体请求。

## 方案对比与决定

采用“现有剧本 + 片段（镜头写在提示词内）+ 统一资产 + 每集制作画布”。视频任务保存通用来源与固定输入，导演输出、视频生成、音频生成共同使用资产层。直接导出和多轨剪辑共用媒体合成能力。片段 AI 复用聊天 Agent、资源工具和 WorkingOverlay 审阅/历史，没有独立 AI 草稿或二次应用流程。

生成配置归片段或视频节点（同一张 ProductionClips），实际输入由明确类型的画布连线表达。任务保存固定快照与通用来源，结果登记为资产；每次只生成一个结果，不满意时明确重做，旧结果保留。导演复用已有工程与版本能力。多轨剪辑纳入本方案，先由 X 交付顺序合成，再由 C 复用同一合成规则交付编辑与预览。

按 2026-10-07 的范围调整，本方案不内置视频模型，只使用用户自行配置的服务地址、密钥和模型，支持 Seedance 2.5、MiniMax H3 与 Wan 3.0。协议适配和配置指引可以随应用提供，但未配置账户时没有可直接调用的视频模型。原方案的内置视频网关、额度冻结和云端结果副本不再属于本次实施范围；文本与图片生成同样使用用户配置的供应商。下表保留技术选型与职责边界；实现和验收状态以任务表为准。

| 能力 | 采用 | 原因与边界 |
|---|---|---|
| 三维导演 | 当前 pubspec.yaml 与 lock 使用 `flutter_scene 0.24.0`，启用 Impeller 与 Flutter GPU | 用户已确认调整渲染器前提；工程、视口与交互统一使用 Dart/Flutter。保持 sqlite3 和现有最低系统范围，Windows / macOS 分别验证运行与主应用性能 |
| 媒体播放 | `media_kit 1.2.6`、`media_kit_video 2.0.1`、`media_kit_libs_video 1.0.7` | 统一 Windows / macOS 视频与音频播放；同时只有一个活动视频播放器。资产和导演参考沿用单素材预览；C 播放低清分段合成缓存，避免多播放器各自计时 |
| 探测与编码 | 当前 `ffmpeg_kit_flutter_new 4.6.7`、`FfmpegRunner` 与 `MediaService`；基础编码参数为 `libx264` / AAC | 复用参数数组、异步会话、取消与 FFprobe；X 完成顺序成片，C 增加多轨合成和区间预览。Windows / macOS 的实际滤镜、编码器和原生包分发分别验收，旧 OpenH264 选型保留为历史依据 |
| 导演预演输出 | MP4，H.264/YUV420P，默认 720×1280、24 fps，支持横屏 | 固定帧捕获与编码，FFprobe 校验后登记资产；模型结果保留其实际规格，整集与剪辑成片分别由 X、C 交付 |
| 视频模型 | 用户自配 Seedance 2.5、MiniMax H3、Wan 3.0 | 分别维护 `ark_video`、`minimax_video_v2`、`wan_video` 适配；按具体模型/接口定义能力，不共用图片协议或默认开放全部参考类型 |
| 外部服务 | 用户配置的模型供应商与 S3 兼容存储 | 视频生成直连供应商，参考文件由客户端上传到用户 Bucket，生成结果下载到本地 |
| 参考上传 F | 用户自配 S3 兼容对象存储 | 复用 E1 的统一参考上传入口，使用全局配置的用户 Bucket，生成结果仍保存本地 |

媒体合成复用锁定的 FFmpegKit 与现有 MediaService/FfmpegRunner；当前软件编码参数为 libx264 / AAC。Windows / macOS 分别验证所需滤镜、编码器与安装包，不能依赖系统 PATH 的 ffmpeg。旧 OpenH264/非 GPL 自建包、三维备选与 SDK 解析记录仅保留在[历史依据](references.md)，不作为当前实现指令。

Flutter GPU 使用已有 flutter_scene 路线，导演与媒体播放/编码需在同一进程验收。上游 issue 状态不构成发布前提；以可复现功能、输出正确性及资源生命周期作为通过条件。变更依赖时复核实际 lock 和平台打包，不根据历史解析结果宣布通过。

## 核心原则与假设

1. ProductionClips 行是生成节点提示词与配置的唯一保存对象；导演工程、资产、任务快照各有明确真源，导航与坐标只影响显示。
2. 视频每次生成一个结果，历史结果保留，不提供同一节点的多候选批量入口。生成任务使用不可变快照，结果保存登记后自动采用；用户可直接发起，也可由 Agent 在任务范围内显式创建生成请求并按权限执行。ask 需批准，allow 可连续执行，deny 禁止提交；失败恢复不自动收费重提。
3. 已接受的任务继续查询和保存；关闭区域不取消任务，提交超时不自动创建第二次收费请求。
4. 本地文件与工程可离线编辑；未支持的模型输入直接说明原因，不暗中丢弃素材或改模型。
5. Windows / macOS 保持相同业务契约和现有最低系统范围；桌面平台构建失败必须修复。移动端不新增短剧制作页面；共享权限设置、审批和分发覆盖 Android，平台不支持的媒体操作明确拒绝，共享层改动不得破坏既有行为。

最脆弱的假设是动态预演能减少构图与走位返工。方案将它输出为普通参考视频，因此效果不佳时作者仍可用静态图、文本或外部素材完成制作，工程与画布不依赖某个视频模型。是否可以对外宣传控制效果，由真实模型对照评测决定。

## H：媒体原生库体积优化

本节定义体积优化的范围与验收，进度见[实施任务](#实施任务) H-01。

当前实现已直接使用 `ffmpeg_kit_flutter_new 4.6.7`，移除旧 `ffmpeg_kit_flutter_new_full` 本地 override 与项目自建媒体脚本；播放继续使用 `media_kit`。当前软件 H.264 编码器为 `libx264`。本文及分篇中此前要求自建非 GPL 包、使用 libopenh264 和维护产物校验的描述属于旧方案，不作为 H 的实现前提；H 不预设恢复自建链。

macOS 当前 Debug App 实测如下，单位为 MiB（文件逻辑大小之和，不重复计算符号链接），均为未压缩体积：

| 项目 | 替换前留存构建 | 当前构建 |
|---|---:|---:|
| App 总体积 | 267.2 | 311.3 |
| FFmpegKit 及其 FFmpeg 库 | 30.6 | 74.9 |
| media_kit 播放库及依赖 | 22.9 | 22.9 |
| 两组媒体原生库合计 | 53.5 | 97.8 |

App 增加约 44.1 MiB，主要来自 FFmpegKit 原生库增大。完整编解码能力和两套 FFmpeg 是待优化对象，但不能将两组库的全部体积都算成可消除的重复。这是 Debug 构建观测，不代表 Release 或安装包增量，也不将其直接设为节省目标。验证状态统一记录在任务表 D1-02，本段仅保留体积比较依据。

任务范围与验收：

1. 先为 macOS 建立相同架构、构建模式与打包方式的基线，分别记录 Release App、分发包和媒体库体积，区分编解码能力、架构切片、符号及重复库的占用。
2. 根据实际调用和导入格式确定最小能力集，保留 FFprobe、现有图片/视频/音频导入与播放、PNG 序列编码、H.264/YUV420P/AAC/MP4 输出、取消与错误处理。不能为缩小体积静默收窄既有导入能力。
3. 比较现成精简包、减少重复媒体依赖和必要时的精简构建，记录实际节省与维护成本后选择最简单可维护的方案，不预先承诺某条技术路线。
